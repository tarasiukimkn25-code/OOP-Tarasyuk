# Звіт: Polly та стратегії відновлення

## Сценарій 1 — зовнішній API

Короткочасні мережеві помилки можуть зникнути самі, тому для ідемпотентного читання використано три обмежені повтори з експоненційною затримкою та jitter. Внутрішній timeout обмежує час окремого виклику. Симуляція спершу повертає дві `HttpRequestException`, потім завершується успішно; окремий повільний виклик переривається timeout-стратегією. Повтори не варто застосовувати до операції, яка може двічі списати кошти.

## Сценарій 2 — база даних

Circuit Breaker спрацьовує після двох послідовних помилок читання, щоб не надсилати нові запити залежності, яка не відповідає. Наступний виклик блокується відкритим ланцюгом і не виконує операцію. Це дає залежності час відновитися, але пороги й час відкриття треба підбирати за метриками системи.

## Сценарій 3 — каталог товарів

Якщо основне джерело каталогу недоступне, Fallback повертає резервне значення з кешу. Користувач отримує відповідь, однак кеш може бути застарілим; застосунок має повідомляти, що дані резервні.

## Очікувані журнали

Під час запуску видно два повідомлення Retry, успішний результат API, timeout для окремого повільного виклику, два збої бази й блокування третього запиту, а також повідомлення про повернення кешованого каталогу. Повні журнали створюються в `dotnet run`.

## Загальні висновки

Retry доречний для коротких тимчасових помилок, timeout обмежує очікування, Circuit Breaker зменшує навантаження на несправну залежність, а Fallback дає контрольовану альтернативу. Ці стратегії потрібно поєднувати відповідно до того, чи можна повторити операцію, наскільки критична свіжість даних і який час очікування прийнятний. Джерело API вибрано за [офіційними прикладами Polly v8](https://github.com/App-vNext/Polly), де сучасний інтерфейс будує pipeline через `ResiliencePipelineBuilder`.
