# Лекція №10. LINQ: оптимізація, розширення та PLINQ

**Тема:** Об'єктно-орієнтоване програмування (C#) | **Виконав:** Тарасюк

## Опис проєкту

У проєкті наведено практичні приклади до **Лекції №10**:

1. **Відкладене виконання LINQ:** запит `Where` виконується під час перебирання, а не під час створення.
2. **Повторне перебирання:** повторне використання запиту знову виконує його умови; `ToArray()` зберігає результат для подальших обчислень.
3. **Оптимізація конвеєра:** спершу фільтруються потрібні елементи, далі формується проєкція, сортування й агрегація.
4. **Метод-розширення:** `InBatches` додає групування до будь-якого `IEnumerable<T>`.
5. **PLINQ:** показано паралельну обробку незалежної CPU-задачі та відновлення порядку через `AsOrdered()`.

## Короткий звіт

### Повторне перебирання й оптимізація

LINQ-запити до `IEnumerable<T>` зазвичай мають відкладене виконання. Якщо послідовність запитати двічі, джерело й усі оператори виконуються двічі. Це може марно витрачати час, а для змінного джерела навіть дати різні результати. Якщо потрібен той самий набір даних кілька разів, його можна матеріалізувати через `ToArray()` або `ToList()`. Матеріалізувати варто лише тоді, коли повторне використання виправдовує пам'ять; для одноразового проходу краще залишити запит відкладеним.

### Коли застосовувати PLINQ

PLINQ корисний для великих обсягів даних і незалежних обчислень, які займають процесорний час: наприклад, перевірки чисел на простоту чи обробки незалежних записів. Його накладні витрати можуть перевищити виграш на малому наборі. Для мережевих запитів, дискового введення-виведення або задач, що вже очікують на інші ресурси, паралельний LINQ зазвичай не є найкращим вибором. У прикладі наведено час послідовної та паралельної обробки; він залежить від обладнання й поточного навантаження.

### Порядок та побічні ефекти

Паралельні гілки можуть завершуватися в іншому порядку, ніж елементи у джерелі. Якщо порядок важливий, слід явно використати `AsOrdered()`, пам'ятаючи про додаткові витрати. Побічні ефекти всередині PLINQ-операторів можуть виконуватися паралельно й у непередбачуваному порядку; спільні змінні можуть вимагати синхронізації. Тому краще використовувати чисті перетворення, а збір результатів робити після завершення запиту.
