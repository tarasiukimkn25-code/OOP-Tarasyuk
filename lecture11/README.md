# Лекція №11. Винятки у .NET: базові патерни й Retry

**Тема:** Об'єктно-орієнтоване програмування (C#) | **Виконав:** Тарасюк

## Опис проєкту

У проєкті наведено практичні приклади до **Лекції №11**:

1. **`try-catch-finally`:** обробка помилки валідації й гарантоване виконання завершального коду.
2. **Власний виняток:** `InvalidPaymentAmountException` надає зрозумілу помилку для некоректної суми.
3. **Патерн Retry:** повторення тимчасової мережевої операції з обмеженням кількості спроб.
4. **Стратегії затримки:** фіксована, лінійна та експоненційна затримки між спробами.
5. **Вибіркові повтори:** через `shouldRetry` повторюються лише тимчасові помилки; помилки валідації одразу передаються виклику. Приклад завершується успішно з третьої спроби після двох тимчасових помилок.

## Короткий звіт: дизайн винятків

Виняток варто кидати, коли операція не може виконати свій контракт: наприклад, невалідний аргумент, відсутній обов'язковий файл або тимчасова відмова зовнішнього сервісу. Звичайний результат краще повертати для очікуваних альтернативних сценаріїв: `null` чи `TryGet...` — коли значення може бути відсутнім; `bool` — для простої перевірки; `Result<T>` — коли очікуваний збій має містити типізовану причину.

Винятки добре підходять для рідкісних збоїв і дозволяють поширити помилку до рівня, який може її обробити. Вони читаються природно у звичайному успішному шляху, однак їх не слід використовувати для частих штатних розгалужень: створення стека викликів коштує дорожче за повернення значення. `Result<T>` явно показує, що операція може завершитись помилкою, але додає перевірки результату в коді. Для великих систем вибір залежить від контракту методу й того, хто здатен відновити роботу.

У демонстрації невалідна сума створює власний виняток, а тимчасова помилка платежу повторюється за допомогою Retry. У реальному застосунку очікувану відсутність запису можна повернути як `null` або `Result<T>`, а помилку конфігурації чи порушення інваріанта — оформити винятком.
